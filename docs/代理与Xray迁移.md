# 本地 Xray 代理迁移

## 运行方式

店铺浏览器与“检测连接”统一使用以下链路：

```text
Chromium / 出口检测 → 127.0.0.1 上的认证 HTTP 入口 → Xray → 用户配置的代理 → 目标网站
                                                    └→ 配置的中转 → 最终代理
```

同时提供认证 SOCKS5 本地入口。SSH、SSR 和 SOCKS4 / 4a 使用本地辅助服务，再由 Xray 提供统一入口。Xray 的 [SOCKS 出站](https://xtls.github.io/en/config/outbounds/socks.html) 实现 SOCKS5，不能依靠配置里写入 `version` 冒充支持 SOCKS4。Xray、SSR 程序均由新项目独立准备、校验和打包，运行时不查找旧项目目录。

| 代理协议 | 支持内容 |
| --- | --- |
| HTTP / HTTPS | 账号密码、CONNECT；HTTPS 支持 SNI 和显式证书校验选项 |
| SOCKS5 / SOCKS4 / SOCKS4a | 独立协议版本；SOCKS4 不接受密码认证 |
| Shadowsocks | Xray 支持的 AEAD / 2022 加密方式 |
| VMess | UUID、alterId、加密方式、TLS、传输参数 |
| VLESS | UUID、TLS / Reality、Vision、SNI、公钥、shortId、传输参数 |
| SSH | 密码认证、远端域名解析、动态 TCP 转发、保活与取消清理 |
| SSR | 独立 SSR helper、加密方式、协议和混淆参数 |

代理管理支持上述协议的新增、编辑、检测与筛选；保留原有地址批量导入，并支持标准 `ss://`、`ssr://`、`vmess://`、`vless://` 分享链接。密码中的空格、引号、反斜杠等字符按原值保存。

编辑窗口可配置中转、最多 8 条备用线路，以及独立的翻译/静态资源代理；可直接填写或复制已有代理的连接信息。复制生成独立连接快照，不递归引用另一个代理的备用池或分流规则。编辑保存影响下一次打开，运行中的店铺继续使用启动时的配置。

VMess / VLESS 的 HTTP 传输 Host 接受域名加端口和方括号 IPv6 加端口，TLS SNI 仍独立校验。SSR 按固定 helper 的实际能力校验加密方式，并统一 `plain`、`chacha20-poly1305`、`xchacha20-poly1305` 等别名；不把 Shadowsocks 2022 当作 SSR 支持项。

## 资源与数据

- Xray 固定为与旧版 Windows 对齐的官方 `1.8.24`，提供 Windows x64、macOS x64 / arm64 资源。
- SSR 固定官方 `0.9.3`，提供 Windows x64 / macOS x64。上游没有原生 macOS arm64 资产，该架构明确返回不支持 SSR。
- `proxy-runtime/manifest.json` 和 `ssr-manifest.json` 记录来源、版本与摘要。准备脚本同时验证下载包、程序及依赖；运行时首次使用验证文件，未变化的文件复用校验结果。
- 打包 hooks 先核验上游资源，再根据实际签名后的文件生成分发清单。Windows 仅接受已跟踪的签名调用产生的变化；macOS 在 helper 签名后、外层 `.app` 封签前更新清单。源码清单保留上游摘要；CI 硬链接先脱离，避免修改源资源。运行时继续严格核验大小及 SHA256。
- V21 增加 `device.proxy_options`，使用项目的加密机制存储高级参数、中转与备用节点。普通列表不返回连接秘密；编辑凭据和启动配置接口按原权限解密返回。
- 更新时省略 `proxyOptions` 保留已有值，显式空对象表示清空；代理连接信息变更后清除旧检测结果。
- 本地入口使用随机账号密码。Chromium 命令行只包含本地地址，插件只对该入口的 HTTP 407 挑战提供本地凭据，不向网页 401 或其他代理发送凭据。
- MV3 在后台脚本加载时同步注册认证监听，读取并验证本地启动配置后即可认证。店铺助手先安装本次启动的 mandatory PAC，再检查远端后台 API，避免重开 profile 时命中旧端口；账号助手不接管代理，仅对启动阶段的网络竞态做有界重试。
- Xray 配置通过标准输入传入；SSR 使用短期临时配置并清理。运行日志不输出上游账号、密码或完整配置。

## 性能和生命周期

相同完整代理配置共享启动任务和 Xray 进程，并按使用者计数释放。不同认证、TLS、中转参数不会误合并；临时检测结束不会关闭店铺仍在使用的代理。需要独立切换线路的店铺使用独立会话。

启动和恢复限制并发，批量检测最多同时处理四个代理。取消检测、退出账号与退出客户端都会清理队列和使用中的检测会话，取消后的结果不写回其他登录会话。

本地端口由操作系统分配，同时预留 TCP / UDP，避开 Windows 的 UDP 排除端口段。就绪检测还核验随机 SOCKS 认证，避免将碰巧监听同端口的其他服务当作当前代理。子进程异常后使用原端口和本地凭据有限恢复，短时间连续恢复失败会关闭受影响店铺。上游错误不会添加 `DIRECT` 出站。

## 线路切换

旧插件的手工切线、检测失败逐线重试、整池测速和选择最快线路保留。检测页从桌面读取实际运行的候选列表、当前选中项和配置摘要；刷新页面不会拿后台新配置覆盖正在运行的旧列表。插件提交候选编号和配置摘要，桌面从启动时取得的授权节点快照选取实际配置；网页无法提交任意代理账号或目标节点。线路清单只包含展示信息，不向插件下发远端凭据。

切换前先用临时会话验证候选出口，通过后替换当前会话的上游，本地端口和本地认证保持不变。切换失败会尝试恢复原线路。插件等待真实成功回执后继续检测，替代旧版固定等待一秒。带备用线路的店铺各自使用独立会话，切换不会改变其他店铺流量。

选定的线路偏好按店铺保存。前后端按同一规则生成配置摘要，旧配置的切换结果不能写到后台的新候选列表；节点参数、绑定设备变化或候选移除会使旧偏好失效。再次打开时验证可用偏好，失败则保留主线并继续有限候选重试。全部失败会显示失败，不使用直连绕过。

总延迟通过选定线路向店铺启动网址发送不带店铺 Cookie/令牌的 HEAD 请求，不接受页面传入测速目标。临时测速不改变当前线路，失败或缺少结果显示 `--`，不会显示虚假的绿色 `0ms`。超时、取消和关闭店铺都会终止探测，包括尚未收到 CONNECT 响应的底层连接。

## 资源代理与分流

参照旧版的独立翻译/静态代理和 PAC 流程，为资源代理单独准备认证的本地 Xray 入口。PAC 优先将资源/CDN 域名交给资源入口，再匹配用户明确填写的直连域名，其他请求使用店铺入口；不自动加入失败直连后备。两类入口的随机账号密码按端口分别提供，不会串用。

每类规则最多 100 项：`example.com` 仅匹配该域名，`*.example.com` 匹配子域名；不接受任意 URL、端口、IP、内网名称或全局通配符。没有配置资源代理时不能保存资源/CDN 域名规则。这里迁移的是域名分流，不包含旧供应商私有 CDN 的域名改写与服务端资源分配。

## 与旧实现的差异

保留旧版的本地 Xray 转发方式，修正配置字符串转义破坏密码、缺少中转时仍引用中转标签、VMess 参数丢失、共享进程提前释放等问题。没有为了提高表面成功率而关闭证书校验，也没有默认开启可能影响上游兼容性的 Mux。

代理检测与浏览器启动走同一配置编译和运行时。固定代理继续校验实际出口与配置的固定 IP；动态代理使用实测出口，换 IP 请求仍通过用户明确配置的供应商 URL 发起。

以下能力需要区分：

- 用户自备静态 / 动态代理、已有节点、中转与备用线路属于本次本地代理迁移。
- 旧供应商的购买、动态住宅资源分配、库存与节点续费依赖原供应商服务。新项目没有可用供应商接入时，不能将本地 Xray 转发宣称为已恢复这些服务。
- SSH / SSR / SOCKS4 辅助节点暂不支持再叠加中转；服务端会提前拒绝不支持的组合。
- SSR 官方 Release 自身拒绝 loopback 上游地址；本机测试 SSR 服务需绑定本机网卡地址。应用的本地监听仍只在 loopback。
- Windows 已做真实转发与 Chromium 认证验证。macOS 资源已校验和验证打包筛选；构建 hooks 已处理签名后的摘要，仍需发布机上的真实证书、macOS 实机及 notarization 验收。自动化测试使用实际 builder 复制/签名调用链配合模拟签名字节，不等于真实签名验收。

## 构建与验证

### 已有店铺的插件升级

Xray 迁移同时调整内置店铺助手，因为 PAC、代理认证、检测页、测速和线路切换需要调用新的桌面接口。两个内置插件随客户端一起构建分发。

2026-11-10 在 `tk全球` 的隔离 profile 副本中确认：只覆盖 unpacked 插件文件，Chromium 仍可能执行旧的 Service Worker，导致新版检测页无法读取线路。此前的新 profile 验证没有覆盖这个升级路径。

现在构建会根据插件全部文件计算 `buildId`，同时写入元数据和后台代码字面量。桌面启动时核对实际执行的后台标识，仅重载不匹配的内置插件并等待标识一致；标识不一致则明确报错，不能仅凭“扩展已启用”认为升级成功。升级不清空店铺 Cookie、扩展存储或浏览器 profile。运行诊断记录每个插件的标识和是否重载，不记录启动凭据。

检测页分别提示店铺信息、线路信息加载失败；尚未执行的检测显示“未检测”。“重新检测”会重新读取详情与当前运行线路后再检测，测速或切线中禁止重置线路列表。

账号助手从已验证的店铺启动配置自行同步账号，不再依赖店铺助手仅发送一次的 LOGIN；并发 LOGIN 共用同一次初始化，失败仍阻止就绪。店铺助手重载会失效旧连接与检测代次，旧异步响应不能把新插件标记为就绪。

重载后的检测页优先复用本插件当前店铺的检测页或空白页，否则新建，不覆盖已有商家标签。未完成检测前的新标签限制保留扩展页面和浏览器内部页面；尚未拿到目标 URL 的新标签延后判断。

`desktop` 的 `npm run test:plugins` 包含持久 profile 升级回归。真实 Chromium 用例需设置 `SPB_PROXY_AUTH_BROWSER=1` 和 `SPB_PLAYWRIGHT_MODULE`，保留同扩展 ID、版本号、目录与 profile，验证缓存旧 worker 升级、已匹配版本不重复重载、升级失败拒绝就绪及 Cookie/扩展存储保留。

本轮升级修复验证共 148 项通过、无跳过：桌面代理 82 项、桌面插件 6 项、插件业务与页面 60 项。页面测试包含项目实际 Vue 渲染器的完整组件挂载与状态更新；构建及 132 个插件文件、178 个资源引用验证通过。

使用已关闭的 `tk全球` profile 隔离副本、合成后端与本机隔离网络，先复现旧 worker 缓存，再通过正式 `preparePlugins → activatePlugins` 升级双插件。实际执行的构建标识与发布包一致，检测页正常挂载，线路读取、网络检查、`CheckCompleted` 完整执行；两个助手及桌面桥均就绪，账号助手单独重载也能恢复。含真实资料的测试副本已清理，源 profile 未打开或修改。当前本地桌面已更新启动，新打开的店铺加载新版插件。

### 扩展管理页闪现与重复检测标签修复（2026-11-10）

旧版同样通过内置扩展的 `contentPage/check.html` 执行检测，但不会先打开 `chrome://extensions/`。新版此前在每次插件激活校验时创建可见的扩展管理标签，再关闭该标签，造成用户观察到的闪现。

现在先核对实际运行的 worker 构建标识；全部匹配时直接返回，不创建控制页面。需要升级时使用 `hidden:true, background:true` 的 CDP target，通过持有该 target 的同一连接完成插件重载。该 target 不出现在标签栏或扩展的标签列表中，连接结束时自动清理；不借用、关闭用户已有的扩展管理页或其他标签。

检测页初始化共用同一个进行中的任务，避免并发创建。恢复的重复检测页仅在扩展 ID、页面路径和店铺 ID 都一致时合并；更新或删除前重新读取标签状态，避免覆盖已经导航到商家页面的标签。完成检测的页面不重复导航。检测未通过前，仅对确认是 HTTP(S) 的新标签执行原有访问限制；扩展页面、浏览器内部页面及已有商家标签不会因该新标签限制被误关。

本轮插件回归 71 项通过（其中 3 项真实 Chromium 用例单独启用执行）；桌面插件回归 7 项通过，覆盖持久 profile 升级、匹配版本免重载、取消升级、失败拒绝就绪以及 Cookie/扩展存储保留。升级相关用例同时断言没有新增可见页面，并保留用户已有的扩展管理页。桌面构建和插件资源校验通过。

另外使用合成后端、隔离网络、正式构建的双插件和同一临时 Chromium profile 连续打开两次；每次均只有一个检测标签、没有可见扩展管理标签，双插件及桌面桥 ready，完成 `CheckCompleted`，无页面脚本错误。独立 CDP 探针也验证隐藏 target 可完成实际 worker 升级，且 `chrome.tabs.query` / `chrome.windows.getAll` 不包含该 target。上述验证均未使用真实店铺 profile，临时资料已清理；本轮不据此宣称真实上游网络始终可用。

### 重开时的出口检测超时修复（2026-11-10）

`tk全球` 的隔离重开测试曾出现本地 CONNECT 已成功、后续 TLS 请求超过 5 秒的情况。同一代理直连实测约 7.6 秒后返回正确出口。对照旧源码需区分两条流程：旧插件对 `ip_type=2/3` 的自有设备直接通过页面 IP 检查；旧 `CheckProxy.probeWhoamiViaProxy` 的实际连通性探测则是串行请求，单服务 8 秒，备用模式 12 秒。新版继续实测出口并校验固定 IP，采用旧连通性探测的串行方式与更合理的等待时间。

代理检测现在单服务最多 8 秒，整轮最多 12 秒，匹配正确出口后立即返回；本机位置查询仍并发运行。每个请求使用独立取消信号，并传入 `HttpsProxyAgent` 的底层 CONNECT，超时、取消、成功和关闭时都会清理连接。初始检测尚未结束时继续复用，结果过期从完成时计算，避免窗口启动较慢时发起重复检测。运行诊断最多记录 8 轮的检测结论、耗时和服务失败分类，不记录代理凭据、响应正文或实测 IP。

SuperPower 检测页自动重试最多一次，修复旧版 `maxRetryTimes > maxRetryNum` 在配置为 1 时实际重试两次的边界问题；手动重新检测会重置次数。总预算内始终未收到有效结果仍显示失败，固定出口不符仍不放行。

本次新增的 9 项网络回归覆盖真实本地静默 CONNECT 的超时/取消释放、备用服务、超过 5 秒的响应、固定出口校验、多出口采样及本机定位取消；另 2 项完整 BrowserHost 生命周期回归验证启动超过 10 秒仍复用检测、启动中关闭可取消并注销会话，相关代理、测速与资源释放 21 项通过。插件回归共 61 项通过，其中 3 项真实 Chromium 用例另行启用执行，覆盖认证、独立资源代理及重开替换旧端口。桌面构建和插件 132 个文件、178 个资源引用验证通过。

使用 `tk全球` 的真实代理、合成店铺后端和同一临时 Chromium profile 完成两轮打开→检测→关闭→重开，出口均匹配，耗时分别约 592ms、329ms；两次均完成 `CheckCompleted`，双插件 ready，无页面脚本错误。临时 profile 和诊断登录已清理，真实店铺 profile/Cookie 未使用。此结果验证本次运行与已修复的超时边界，不保证上游线路今后始终可用。

### 原 Xray 迁移验收

在 Web 目录执行 `npm run build`，再在 desktop 目录执行 `npm run build`。桌面构建会准备当前平台代理资源、构建插件并复制 Web 产物。

desktop 的 `npm run test:proxy` 覆盖配置编译、真实代理转发、共享引用、并发启动、取消、恢复、认证和失败不直连。设置 `SPB_XRAY_TEST_PATH` 为本项目准备的可执行文件，可额外验证各传输配置被真实 Xray 接受。

插件认证和启动的真实 Chromium 测试位于 `super-power-browser-plugins/scripts/proxy-auth.test.mjs` 和 `proxy-bootstrap.test.mjs`，设置 `SPB_PROXY_AUTH_BROWSER=1` 和 `SPB_PLAYWRIGHT_MODULE` 后运行。测试使用临时 profile、本机代理与本机目标，不使用真实店铺；重开用例复用同一临时 profile，并显式重放上次的过期 PAC，验证新端口在后台请求前生效。当前 Chromium 144 的 unpacked 扩展重开不会稳定保留旧 PAC，因此这个用例验证的是受控旧状态恢复，不代表自然复现了持久化故障。

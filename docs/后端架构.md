# 后端架构

采用模块化单体，API 和 Worker 分进程运行，共用业务模块和 MySQL 数据库。按核心功能划分边界，不按旧接口数量拆服务，也不为未迁移功能预建模块。

```text
super-power-browser-server/
├─ api/                       HTTP、认证过滤器、请求与响应转换
├─ core/                      业务规则和持久化实现
│  └─ com.superpower.browser/
│     ├─ auth/                登录会话、成员、角色和功能权限
│     ├─ environment/         店铺环境、资源授权、启动配置
│     ├─ device/              三类设备、绑定校验、代理配置
│     ├─ billing/             商品报价、订单、支付、余额和账本
│     ├─ runtime/             内核清单、原生凭据、必要插件
│     └─ shared/              错误、审计和基础持久化工具
└─ worker/                    后台任务入口、调度与任务认领
```

每个业务域内部由业务服务执行规则与事务，由 Repository 管理 SQL。Controller 只做输入输出适配，不直接写 SQL、扣余额或调用供应商。低层 SQL 工具只供 Repository 使用，不作为模块间的业务接口。

跨域依赖按业务方向保持明确：店铺模块通过设备访问接口检查绑定和读取启动所需代理；通过成员查询接口验证被授权成员。账务模块通过设备交付接口推进已支付订单，不能随意更新店铺或权限表。查询所需跨表关联可以在专用查询方法中完成，不因此复制其他域的写入规则。

订单、支付、钱包与账本先放在同一业务域，保持资金事务内聚：余额校验、扣款、流水和订单支付状态一起提交；支付成功与资源交付分开。外部支付和设备供应调用在事务外执行，通过可恢复任务推进。Worker 调用相同业务服务，不复制计价、扣款、授权或交付规则。

内核与插件的旧接口集中在 `runtime` 适配器，并标记 `TODO(runtime-replacement)`。其他模块只依赖新系统的运行资源契约，不感知旧 URL、加密字段或旧令牌。设备供应和支付接入使用独立接口，未配置时报告未配置；不允许通过这些接口调用旧设备或费用服务。

核心测试验证可观察业务结果：功能权限与店铺范围交叉校验、权限撤销后拒绝访问、设备类型限制、余额并发扣款与支付幂等、支付和交付状态分离。构建边界与这些业务测试共同约束后续修改。

设备资源访问同样收口到设备域：企业所有者可访问企业设备；普通成员可访问自己创建的设备，以及自己拥有或获授且未回收店铺所绑定的设备。新增自有设备允许创建者后续检测、编辑及绑定，这是新系统针对创建流程的简化规则。列表、详情、编辑、连接凭据和启动代理复用同一资源范围。启动店铺检查 `shop.open` 与店铺授权，不额外要求设备管理权限。

当前代码已拆分 `AuthController`、`EnvironmentController`、`DeviceController`、`BillingController`、`RuntimeController`，对应业务服务和包内 Repository。`EnvironmentService` 通过 `MemberDirectory`、`DeviceAccess` 使用其他业务域；数据库查询留在 Repository。初始化管理员通过独立 `ApplicationRunner` 的事务创建企业、用户和余额账户，避免同一对象内调用导致事务注解不生效。

`BillingService` 负责订单用例与外部支付编排，`OrderTransactions` 单独负责本地资金事务；`DeliveryTransactions` 将本地设备交付和订单完成状态一起提交，外部供应调用留在事务外。`BackgroundOperations` 是后台用例入口，Worker 只负责定时唤起。`PaymentGateway` 和 `DeviceSupplier` 是真实外部替换边界，目前使用明确报告未配置的实现；业务规则仍可独立集成测试。

店铺与代理密码通过 `SecretCipher` 使用 AES-GCM 加密存储；运行时仅在经过权限与资源范围校验后读取。登录密码单独使用 BCrypt 哈希，会话只存令牌哈希。密钥从 `APP_DATA_KEY` 注入，不写进源码或返回前端。

实际验收状态以 [迁移状态](迁移状态.md) 为准，架构分层完成不代表支付商户、设备供应或定制内核已经接通。
